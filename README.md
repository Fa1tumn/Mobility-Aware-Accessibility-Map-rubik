# Mobility-Aware-Accessibility-Map-rubik

Each collection iteration produces one database record, with null fields for unavailable devices. The phone supplies GPS only; a separate IMU supplies motion samples. `main.py` collects the frame, GPS and IMU window, runs surface inference, combines their outputs, and asks `storage.py` to save the record.

## Data flow

```mermaid
flowchart LR
    A[Phone] -->|HTTP POST /gps| B[phone.py]
    C[Independent IMU] -->|BLE notifications| D[imu.py]
    E[CSI camera] -->|GStreamer JPEG pipe| F[vision.py]
    B -->|GPS dictionary| G[main.py]
    D -->|IMU window and metrics| G
    F -->|BGR frame and timestamp| G
    G -->|Image| H[inference.py]
    H -->|Surface result| G
    G -->|Combined record| I[storage.py]
    I --> J[observations.sqlite3]
    J -->|Read local rows| K[upload_supabase.py]
    K -->|HTTPS JSON| L[Supabase observations]
```

| File | Input -> processing -> output |
| --- | --- |
| `phone.py` | GPS JSON over HTTP -> validate fields and add receive times -> latest GPS dictionary. |
| `vision.py` | JPEG bytes from GStreamer stdout -> decode and keep the latest image in a queue -> BGR image with frame timestamps. |
| `imu.py` | WT901BLE binary notifications -> split 20-byte packets, convert units and buffer samples -> two-second window, slope and average vibration frequency. |
| `inference.py` | BGR image -> resize, normalize, run QNN/HTP and parse masks -> largest surface region's label and confidence. |
| `main.py` | Frame, GPS and module results -> check GPS timing/accuracy and combine fields -> record dictionary. |
| `storage.py` | Record dictionary -> parameterized SQLite INSERT -> saved row and record ID. Adds missing IMU columns to old databases. |
| `test_pipeline.py` | Run the full pipeline once, then inject five cases into the modules separately -> check their combined records -> console results and `test_observations.sqlite3`. |
| `upload_supabase.py` | Read SQLite rows -> convert boolean/JSON fields -> send batches to Supabase REST API and print upload counts. |

## Actual inputs and outputs: test case 1

The examples below show what each module receives and returns in stage 2, case 1. Numeric results are rounded; timestamps change each run.

### 1. Phone GPS

`inject_phone()` sends this JSON to `POST /gps`:

```json
{
  "latitude": 37.502789,
  "longitude": 126.9905,
  "accuracy_m": 2.9
}
```

`phone.py` validates latitude, longitude and accuracy. The HTTP response is `200` with `{"ok":true}`. `get_latest_gps()` returns these three fields plus `gps_time` (Pi receive time in UTC) and `gps_monotonic` (Pi monotonic clock for time comparisons).

### 2. Camera image

`inject_camera()` creates a uniform gray image, encodes it as JPEG, and writes the JPEG bytes into a pipe. The normal reader in `vision.py` decodes those bytes and queues the frame.

```text
Image shape: (24, 32, 3)
Data type: uint8
Every BGR pixel: [169, 169, 169]
```

`capture_frame()` returns a dictionary containing `image` (the BGR array), `frame_time` (UTC decode time), and `frame_monotonic` (Pi monotonic decode time). The image goes to inference; the frame time becomes the final record time.

### 3. IMU samples

`inject_imu()` generates 200 binary packets representing 100 samples per second. It splits the byte stream partway through a packet to check buffering, then sends the remaining packets together. The first packet is shown in hexadecimal:

```text
55 61 3E FF 00 00 08 08 00 00 00 00 00 00 00 00 00 00 00 00
```

`55 61` identifies a sample. The remaining bytes hold nine signed, little-endian 16-bit values: acceleration XYZ, angular velocity XYZ, and angle XYZ. `decode_packet()` converts acceleration and angular velocity into this dictionary; angles are currently unused:

```json
{
  "timestamp_s": 0.01,
  "ax": -0.92895,
  "ay": 0.0,
  "az": 9.844957,
  "gx": 0.0,
  "gy": 0.0,
  "gz": 0.0
}
```

`timestamp_s` is generated by `receive_data()` and increases by 0.01 seconds; it is not transmitted by this default packet format. `ax/ay/az` are acceleration including gravity, in m/s^2; `gx/gy/gz` are angular velocity, in rad/s. This case simulates a calibrated IMU with x forward and z upward, a -9.5% slope and a 15 Hz vibration. Binary quantization slightly changes the generated values. The test aligns the sample window to the camera frame.

The packets pass through `receive_data()`, `decode_packet()` and `add_sample()`. `get_window()` selects samples before the frame; `analyze_samples()` calculates:

```json
{
  "slope_percent": -9.5,
  "vibration_frequency_avg_hz": 15.0
}
```

Slope comes from mean gravity components during near-static motion. Average vibration frequency is the power-weighted mean from 1 to 40 Hz of the acceleration magnitude signal, with at least 80 samples/s. These values are calculated from the samples. The slope/frequency targets are parameters used to generate the test packets.

### 4. Surface inference

`inference.py` receives the BGR image from the camera. It resizes to 640x640, converts to RGB, divides by 255, and writes a float32 tensor shaped `[1, 3, 640, 640]`.

The test replaces QNN execution with `simulate_qnn()`. It creates zero-filled output tensors and sets these values before writing the `.raw` files:

```python
boxes[0, 0] = [320, 320, 640, 640]
class_scores[0, 0] = [0, 0.78, 0, 0, 0, 0, 0]
mask_coefficients[0, 0, 0] = 1.0
prototypes[0, :, :, 0] = 1.0
```

Class order is `blocks, cement, asphalt, urethane, soil_stone, other, damaged`. The second score selects `cement`. The box covers the full 640x640 input; the mask values create a full-image surface region.

The normal inference code reads the raw files, filters predictions and selects the largest mask. `analyze_image()` returns:

```json
{
  "surface_label": "cement",
  "surface_confidence": 0.78,
  "objects_supported": false,
  "objects": null
}
```

This prediction is supplied by the test. Recognition accuracy requires a real model and real images. Object detection is currently commented out.

### 5. Combine and save

`main.py` checks that GPS and frame times differ by at most 1 second and GPS accuracy is at most 10 meters. It passes the module outputs to:

```python
record = main.combine_data(frame, gps, result, imu_result)
record_id = storage.save_record(connection, record)
```

The frame supplies `record_time`; GPS supplies latitude/longitude; inference supplies the surface and reserved object fields; the IMU supplies slope/frequency. SQLite adds `id`. The saved row for this case is:

```json
{
  "id": 1,
  "record_time": "2026-10-13T13:22:36.034114Z",
  "latitude": 37.502789,
  "longitude": 126.9905,
  "surface_label": "cement",
  "surface_confidence": 0.78,
  "slope_percent": -9.5,
  "vibration_frequency_avg_hz": 15.0,
  "objects_supported": 0,
  "objects": null
}
```

SQLite stores `False` as `0` and `None` as `NULL`. GPS accuracy and monotonic timestamps are used for checks; the database stores the combined fields shown above.

### Check the Bluetooth IMU separately

The detected device is `WT901BLE68`, address `C8:2C:72:8F:2B:2C`. `imu.py` connects directly using Bleak; a manual `bluetoothctl connect` is unnecessary. Disconnect any phone app connected to the IMU before running:

```bash
/home/ubuntu/test/.venv/bin/python -B imu.py
```

Bleak and NumPy are already installed in this environment. Each connection configures 100 Hz output and 42 Hz bandwidth, then subscribes to notifications. It does not issue a flash-save or calibration command. Press Ctrl+C to disconnect.

| Connection setting | Value |
| --- | --- |
| Notify characteristic | `0000ffe4-0000-1000-8000-00805f9a34fb` |
| Write characteristic | `0000ffe9-0000-1000-8000-00805f9a34fb` |
| Supported sample format | Default `55 61`, 20 bytes |
| Register replies | `55 71` packets are skipped |

The terminal prints received samples per second, window size, acceleration, angular velocity and metrics. A live check received about 100 samples/s, often bundled as four samples in one 80-byte notification. The receiver handles both split and bundled packets. See the [manufacturer protocol](https://wit-motion.yuque.com/wumwnr/docs/gpare3) and [official Python SDK](https://github.com/WITMOTION/WitBluetooth_BWT901BLE5_0).

Default packets have no device timestamp or sequence number. The receiver assigns times at the configured sampling interval and initially aligns the latest sample in a batch to the Pi receive clock. Small timing corrections follow slow clock drift; a timing mismatch over 0.25 seconds clears the window and realigns it. Bluetooth delay or lost samples can still affect alignment and frequency accuracy; the reported frequency is approximate. Optional extended/timestamp packet formats are not supported; keep the default output format.

`Waiting for recent IMU samples` means no usable recent window is available. It is expected during connection. The printed `received_rate_hz` distinguishes ongoing reception from zero received samples during that reporting interval. Samples more than 0.15 seconds behind the current time are rejected.

Keep `mounting_calibrated` false until the sensor is fixed to the platform with x forward and z upward, and its sensor/axis calibration has been verified. Then enable it in `imu.py`. Uncalibrated mounting yields NULL slope; no meaningful vibration yields NULL frequency. Missing, stale or unsuitable IMU data also yields NULL metrics. GPS and image collection can continue without valid IMU metrics. Set `device_address` to `None` to disable BLE.

## Upload to Supabase

The standalone uploader can send saved records separately: SQLite -> JSON batches -> HTTPS POST -> Supabase. `main.py` can also upload each saved observation when an explicit Supabase URL and key are configured (see below). It reads a snapshot of all local records without changing SQLite. Each run upserts by `(source_id, record_time)`, so sending the same records again updates them. A failure stops the upload; rerun after fixing the error. It uses the Python standard library.

| Function | Input -> output |
| --- | --- |
| `read_records(db_path)` | SQLite path -> list of record dictionaries; converts `objects_supported` to boolean and stored `objects` text to JSON. |
| `upload_records(records, supabase_url, api_key)` | Records and connection values -> sends batches of 100 to `/rest/v1/observations` -> uploaded count. |
| `main()` | Database argument and environment variables -> reads records, uploads, prints progress; exits with code 1 on error. |

Get the project URL from the Supabase dashboard's Data API/Connect screen and a **Secret key** (`sb_secret_...`) from **Settings > API Keys**. Store them as `SUPABASE_URL` and `SUPABASE_SECRET_KEY`. This key is for a private upload environment you control; keep it out of source code, GitHub and chat. A legacy `service_role` key can instead use `SUPABASE_SERVICE_ROLE_KEY`. New keys use the `apikey` header; legacy JWT keys also use `Authorization: Bearer` ([API keys](https://supabase.com/docs/guides/getting-started/api-keys)).

`SUPABASE_URL` accepts either `https://your-project.supabase.co` or `https://your-project.supabase.co/rest/v1/`. The uploader builds `/rest/v1/observations` once and prints the destination URL. HTTP 404 with `PGRST125` means the request path is invalid; check for a repeated `/rest/v1` or a table name appended to the configured base URL.

For a new destination table, run this once in the Supabase SQL Editor. The script expects these columns and the unique `(source_id, record_time)` key. An existing table needs the same schema; `CREATE TABLE IF NOT EXISTS` leaves an existing schema unchanged.

```sql
CREATE TABLE IF NOT EXISTS public.observations (
    id bigserial PRIMARY KEY,
    source_id bigint NOT NULL,
    record_time timestamptz NOT NULL,
    latitude double precision,
    longitude double precision,
    surface_label text,
    surface_confidence double precision,
    slope_percent double precision,
    vibration_frequency_avg_hz double precision,
    objects_supported boolean DEFAULT false,
    objects jsonb,
    UNIQUE (source_id, record_time)
);
ALTER TABLE public.observations ENABLE ROW LEVEL SECURITY;
GRANT SELECT, INSERT, UPDATE ON public.observations TO service_role;
GRANT USAGE, SELECT ON SEQUENCE public.observations_id_seq TO service_role;
```

Enable the project's Data API with the `public` schema exposed. In a Bash terminal, set the URL, enter the key at the hidden prompt, and upload the five sample records:

```bash
export SUPABASE_URL="https://your-project.supabase.co"
read -rsp "Supabase secret key: " SUPABASE_SECRET_KEY
export SUPABASE_SECRET_KEY
printf '\n'
python3 upload_supabase.py test_observations.sqlite3
```

For collected observations, run `python3 upload_supabase.py` (default: `observations.sqlite3`). A successful sample upload prints `Uploaded 5/5 records.` and `Upload complete: 5 records sent to observations.` SQLite `0` becomes JSON `false`; `NULL` stays JSON `null`. Local IDs are sent as `source_id`; Supabase generates the cloud `id`. Uploading the same `(source_id, record_time)` again updates the existing row without changing its cloud ID. IDs increase but may have gaps after retries. `CONFIG` in the script sets the table, batch size and timeout. Query the destination with `SELECT * FROM public.observations ORDER BY record_time, id;`.

### Partial device failures and automatic uploads

`main.py` keeps collecting when camera, GPS, IMU startup/read, or image inference fails. Only the affected fields become SQL `NULL` / JSON `null`. Missing, stale, or inaccurate GPS clears the coordinates without dropping the observation. Without a camera frame, the observation uses the current UTC time and IMU/GPS are aligned to the current monotonic time. Devices that fail to start remain unavailable until the next run; reads and inference are attempted again each iteration.

Set `SUPABASE_URL` and `SUPABASE_SECRET_KEY` (or `SUPABASE_SERVICE_ROLE_KEY`) as described above, then run `python3 main.py`. Each observation is committed to SQLite before upload. Upload failures are retried on the next iteration; after a restart, use `python3 upload_supabase.py` to upload any saved backlog. Without an explicit URL and key, collection continues locally with a startup message.

For existing Supabase tables, allow an unavailable camera/inference output to be null:

```sql
ALTER TABLE public.observations ALTER COLUMN objects_supported DROP NOT NULL;
```

### Supabase IDs across restarts

The cloud `id` is allocated by a PostgreSQL sequence, independently of SQLite. The uploader omits `id` and sends the local ID as `source_id`. Even if a fresh local database starts again at 1, observations with a different `record_time` receive new cloud IDs. The `(source_id, record_time)` unique key prevents duplicate rows on upload retries.

Before running the updated uploader against an existing table, stop collection/upload processes and run **`supabase_cloud_ids.sql`** in the Supabase SQL Editor. It preserves all observations, copies old IDs into `source_id`, and assigns new IDs only to existing rows with duplicate IDs (the earliest row for each ID keeps it). Existing foreign keys or external references to duplicate IDs require review before migration. The sequence continues above the current maximum. This migration has not been applied to your remote database.

After migration, restart `main.py` and sort the Supabase table by `id` ascending to inspect newly allocated IDs. Local `Saved record ...` log IDs remain SQLite IDs; they can differ from cloud IDs. IDs are unique and increasing, not guaranteed to be consecutive.

PostgreSQL sequence allocation can leave gaps after retries; see the [PostgreSQL sequence documentation](https://www.postgresql.org/docs/current/functions-sequence.html). The upload request uses a unique conflict key as described in the [PostgREST upsert documentation](https://docs.postgrest.org/en/stable/references/api/tables_views.html#upsert).
